# Messenger — лабораторна робота 7 (варіант 1, розширений до месенджера)

TCP клієнт-серверний месенджер на Python: акаунти, особисті діалоги, загальний канал,
офлайн-доставка, статуси повідомлень (✓ / ✓✓ / синє ✓✓), індикатор «друкує…», історія в SQLite,
графічний клієнт на tkinter. Лише стандартна бібліотека.

## Запуск

```bash
# 1. сервер
python server.py                 # --host 0.0.0.0 --port 5050 --db messenger.db -v

# 2. клієнти (запустіть кілька копій; на вкладці входу — "Реєстрація" для нового акаунта)
python client.py                 # --host <IP сервера> --port 5050

# 3. навантажувальний тест (сервер має працювати)
python bench.py --clients 10 50 100 200 --msgs 20 --rate 10
```

Інтерфейс клієнта стилізований під Telegram (світла тема). Зображення лежать у `assets/`
(`logo.png` — аватар каналу, `logo_big.png` — екран входу, `wallpaper_logo*.png` — шпалери чату);
без них клієнт теж працює.

Вимоги: Python 3.10+. На Linux для tkinter може знадобитись `sudo apt install python3-tk`.

## Топологія

```
 ┌────────────┐                    ┌──────────────────────────┐
 │ Клієнт A   │◄──── TCP :5050 ───►│  Сервер                  │
 │ (tkinter)  │                    │  ┌────────────────────┐  │
 └────────────┘                    │  │ accept-цикл        │  │
 ┌────────────┐                    │  └─────────┬──────────┘  │     ┌──────────┐
 │ Клієнт B   │◄──── TCP :5050 ───►│   потік на клієнта     │◄───►│ SQLite   │
 └────────────┘                    │  (Session) + Hub       │     │ users,   │
 ┌────────────┐                    │  (хто онлайн)          │     │ messages │
 │ Клієнт C   │◄──── TCP :5050 ───►│                        │     └──────────┘
 └────────────┘                    └──────────────────────────┘
```

Клієнти з'єднуються **лише з сервером**; повідомлення між клієнтами йдуть через нього
(зіркоподібна топологія). Кожне з'єднання обслуговує окремий потік (мультипоточність).
У клієнта окремий потік читає сокет і передає події в GUI через `queue.Queue`.

## Протокол

TCP, UTF-8, один JSON-об'єкт на рядок (`\n`). Це вирішує проблему меж повідомлень у потоці TCP
(в оригінальному прикладі з методички `recv(1024)` міг склеїти або розрізати повідомлення).

| Напрям | `type` | Поля | Призначення |
|---|---|---|---|
| C→S | `register` / `login` | `user`, `password` | Реєстрація / вхід |
| C→S | `msg` | `to`, `text`, `cid` | Повідомлення користувачу або в `#general` |
| C→S | `history` | `with` | Запит історії діалогу (до 100 останніх) |
| C→S | `read` | `with` | «Я прочитав діалог» |
| C→S | `typing` | `to` | Користувач друкує |
| C→S | `ping` | `t` | Вимір RTT |
| S→C | `auth_ok` / `auth_err` | `users[]` / `text` | Результат входу; список контактів із online/unread |
| S→C | `msg` | `id`, `from`, `to`, `text`, `ts` | Вхідне повідомлення |
| S→C | `ack` | `cid`, `id`, `ts`, `status` | Підтвердження збереження (0 — надіслано, 1 — доставлено) |
| S→C | `delivered` | `to` | Одержувач увійшов і отримав офлайн-повідомлення |
| S→C | `read` | `by` | Співрозмовник прочитав діалог |
| S→C | `presence` | `user`, `online` | Зміна статусу онлайн (також поява нового користувача) |
| S→C | `history`, `typing`, `pong`, `error` | — | Відповіді |

## Таблиця функцій

| Функція | Реалізація |
|---|---|
| Реєстрація та вхід | PBKDF2-HMAC-SHA256 (100 000 ітерацій, сіль 16 байт), `compare_digest` |
| Особисті повідомлення | Маршрутизація через `Hub`, збереження в SQLite |
| Загальний канал `#general` | Розсилка всім онлайн, історія 100 повідомлень |
| Офлайн-доставка | Повідомлення зберігаються; при вході — лічильник непрочитаних + `delivered` відправникам |
| Статуси | `…` в обробці · `✓` надіслано · `✓✓` доставлено · синє `✓✓` прочитано |
| Presence | ● в мережі / ○ не в мережі, оновлюється в реальному часі |
| «Друкує…» | `typing` не частіше ніж раз на 2 с, зникає через 2.5 с |
| Лічильник непрочитаних | Підраховується на сервері, показується в списку контактів |
| Кілька вкладок одного акаунта | Повідомлення дублюються в усі сесії користувача |
| Виміри RTT | `ping`/`pong` кожні 5 с, показано в клієнті |
| Захист | Ліміт рядка 64 КБ, тексту 2000 символів, валідація імені, обробка розриву з'єднання |

## Сценарії використання (кейси для звіту)

1. **Реєстрація і вхід.** Запустити сервер і два клієнти → зареєструвати `alice` і `bob`.
   Помилкові випадки: зайняте ім'я, неправильний пароль, занадто коротке ім'я.
2. **Особисте листування онлайн.** `alice` пише `bob` → у `bob` з'являється повідомлення;
   у `alice` тік змінюється `✓✓`; коли `bob` відкриє діалог — тіки стають синіми.
3. **Офлайн-доставка.** `bob` закриває клієнт; `alice` пише → один сірий `✓`.
   `bob` входить: у списку `alice (1)`, у `alice` тік стає `✓✓`.
4. **Загальний чат.** Відкрити «Загальний чат», написати з одного клієнта — бачать усі онлайн.
5. **Presence і «друкує…».** Закрити/відкрити клієнт — ● / ○ змінюється у всіх; набір тексту
   показує «друкує…» співрозмовнику.
6. **Втрата з'єднання.** Зупинити сервер → клієнт показує попередження і повертається на екран входу.
7. **Навантаження.** `python bench.py ...` (див. нижче).

## Продуктивність

Тест `bench.py`: N клієнтів, кожен надсилає 20 особистих повідомлень (10 повідомлень/с на клієнта)
наступному клієнту в кільці. Затримка = час від `send` до отримання одержувачем (включає запис в SQLite).
Виміряно в одній Linux-VM, клієнти й сервер на `127.0.0.1` (Python 3.13):

| Клієнтів | Надіслано | Отримано | Втрати | Середня вхід., мс | Затримка avg, мс | p95, мс | max, мс | Пропуск., повід./с |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 10 | 200 | 200 | 0 % | 101 | 1.6 | 9.8 | 12.6 | 99 |
| 50 | 1000 | 1000 | 0 % | 400 | 1.6 | 9.3 | 13.5 | 491 |
| 100 | 2000 | 2000 | 0 % | 745 | 5.4 | 14.9 | 25.9 | 979 |
| 200 | 4000 | 4000 | 0 % | 2021 | 7.2 | 21.2 | 30.0 | 1872 |

Висновки:
- Жодного повідомлення не втрачено до 200 одночасних клієнтів; середня затримка < 10 мс на loopback.
- Затримка зростає з кількістю клієнтів через GIL і єдиний SQLite-коннекшн під м'ютексом
  (кожне повідомлення — окремий `commit`).
- Час входу ~ лінійно росте від навантаження: PBKDF2 навмисно повільний (захист від підбору пароля),
  а під GIL хеші рахуються послідовно.
- Модель «потік на клієнта» проста, але на тисячах клієнтів дорога по пам'яті й перемиканню контекстів;
  масштабування — `asyncio` та пакетні записи в БД.
- Тест на loopback не враховує реальну мережу; для оцінки в LAN запустіть сервер і `bench.py` на різних машинах.

## Відмінності від базового прикладу з методички

| Базовий приклад | Тут |
|---|---|
| `recv(1024)` без меж повідомлень | JSON-рядки, буферизоване читання |
| Розсилка всім, крім відправника | Адресна маршрутизація + загальний канал |
| Анонімні `addr` | Акаунти з хешованими паролями |
| `list` клієнтів без блокувань | `Hub` з м'ютексом, `send`-лок на сокет |
| Консоль | GUI на tkinter |
| Немає збереження | SQLite: історія, офлайн-доставка, статуси |
